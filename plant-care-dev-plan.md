## 1. Объём MVP

**Делаем:**

- Регистрация/вход (email + пароль), один пользователь видит только свои растения.
- CRUD растений и событий ухода (поля и категории — как в прототипе).
- Планировщик, который раз в сутки проверяет, какие события «созрели», и ставит задачу на отправку.
- Отправка напоминаний в три канала: **MAX**, **VK**, **Telegram**. Уведомление уходит ровно в те каналы, которые выбраны в событии, **без приоритетов и фолбеков** (не доставилось в один канал — в другой не переотправляем). Email используется **только для служебных писем** (сброс пароля, раздел 8), не как канал напоминаний; push — не делаем в MVP (см. раздел 13).
- Страница подключения каналов: пользователь сам привязывает свой MAX/VK/Telegram к аккаунту.
- Деплой на один VPS с датацентром в РФ.

**Сознательно не делаем** — см. раздел 13 (non-goals), чтобы не разрастись раньше времени.

## 2. Стек технологий (решено, не обсуждаем заново)

| Слой | Выбор | Почему именно так |
|---|---|---|
| Backend-язык | **Go**, стандартная библиотека `net/http` + `chi` (лёгкий роутер, не фреймворк) | Минимум зависимостей, один бинарник |
| БД | **PostgreSQL** | Единственная стейтфул-зависимость; `advisory lock`/`SELECT ... FOR UPDATE SKIP LOCKED` закрывают и идемпотентность планировщика, и outbox-очередь отправки — без Redis/RabbitMQ |
| Миграции | `goose` или `golang-migrate` (любой, на выбор агента) | Просто, без ORM-магии |
| Доступ к БД | `database/sql` + `sqlc` (генерация типобезопасных запросов из SQL) **или** просто ручные репозитории — без тяжёлого ORM (gorm и т.п. не брать) | Меньше магии, проще читать сгенерированный SQL |
| Планировщик | Goroutine с `time.Ticker` **или** `robfig/cron` внутри того же бинарника | Без внешних крон-систем и без GitHub Actions |
| Recurrence | `teambition/rrule-go` для календарных правил (RFC 5545) | См. раздел 5 — не для всех событий, см. нюанс там же |
| Auth | Email + пароль, `argon2id` для хэша, server-side сессии (не JWT) | Проще отозвать сессию, меньше токен-менеджмента для MVP |
| Frontend | **React** (Vite), без UI-кит-библиотек — чистый CSS по токенам прототипа (цвета/шрифты уже определены в HTML-прототипе, перенести как CSS custom properties) | Прототип уже содержит готовую дизайн-систему, не нужно тащить MUI/AntD |
| Деплой фронта | Собранный `dist/` **встраивается в Go-бинарник через `go:embed`** и раздаётся тем же процессом | Один бинарник, один процесс, один порт — никакого отдельного фронтенд-хостинга/CDN |
| Хостинг | VPS в РФ — **Timeweb Cloud или Beget** для старта (см. раздел 9 анализа) | Дёшево, датацентр в РФ, подходит под 152-ФЗ при выборе российского региона |
| Служебная почта | Пакет `/internal/mailer`, SMTP (`net/smtp` или `wneessen/go-mail`) | Только письма сброса пароля; не канал напоминаний |
| API-документация | **OpenAPI 3.1 (spec-first, файл `api/openapi.yaml`) + Swagger UI**; валидация/сверка через `getkin/kin-openapi` | Спека — единственный источник правды для API; см. раздел 8.1. Swagger UI раздаётся из встроенных (`go:embed`) статических файлов `swagger-ui-dist`, без CDN |
| Контейнеризация | Docker Compose: `app` (Go-бинарник) + `postgres` + `caddy` (TLS/reverse proxy) | Caddy сам получает Let's Encrypt-сертификат, не нужно руками возиться с nginx+certbot |

/internal

  /plants              — Plant, CareEvent: CRUD, работа с recurrence (rrule-go)

    linking.go         — логика привязки канала к пользователю (коды подключения, вебхуки)
  /api                 — HTTP-роутинг, DTO, склейка доменов для фронтенда

  /src/components

Правило: **`/internal/plants` и `/internal/scheduler` не импортируют ничего из `/internal/sender/max|vk|telegram` напрямую.** Они видят только `sender.Dispatcher` (интерфейс) и кладут generic-задачи в очередь. Это и есть требование «блок с сендером — отдельная доменная область»: сегодня это MAX/VK/Telegram, завтра можно добавить канал, не трогая ни планировщик, ни модель растений.

## 4. Модель данных

```sql
users (
  id, email UNIQUE, password_hash, created_at,
  city_id FK -> cities   -- город пользователя, из него берётся часовой пояс; выбирается при регистрации, меняется в /account
)

cities (                     -- справочник городов РФ, только чтение, наполняется сидом/миграцией
  id, name, region, timezone,   -- timezone — IANA-имя (Europe/Moscow, Asia/Yekaterinburg, ...)
  population, lat, lon
)
-- Источник: открытый перечень городов РФ с IANA-поясами, например дамп GeoNames по стране RU
-- (лицензия CC BY 4.0, нужна атрибуция в /api/docs и в подвале) — финальный источник выбрать на этапе реализации.
-- Часовой пояс пользователя НЕ хранится отдельно: всегда берётся из cities.timezone.

plants (
  id, user_id FK, name, emoji, created_at
)
-- без species/location — сознательно убраны из прототипа как лишние поля (см. историю правок)

care_events (
  id, plant_id FK, title, category, description,
  recurrence_kind   -- enum: 'rrule' | 'manual', см. раздел 5
  recurrence_rule   -- текст RRULE, nullable (используется только при kind='rrule')
  recurrence_note   -- человекочитаемый текст («ежегодно, до распускания почек») — показывается всегда
  next_due_at       -- DATE (в часовом поясе города пользователя), источник истины для планировщика в любом случае
  last_notified_for -- DATE, nullable: для какой next_due_at уже создан уведомляющий job (защита от повторов, в т.ч. для kind='manual')
  channels          -- какие каналы слать для этого события: массив enum ('max','vk','telegram')
  active            -- boolean
)

user_channels (
  id, user_id FK, channel enum('max','vk','telegram'),
  external_id,      -- user_id/chat_id на стороне платформы
  status enum('pending','connected','disconnected'),
  link_code, link_code_expires_at,   -- одноразовый код подключения, см. раздел 7
  connected_at
)
UNIQUE(user_id, channel)

notification_jobs (           -- outbox: и очередь отправки, и лог/история одним махом
  id, care_event_id FK, user_id FK, channel,
  scheduled_at, status enum('pending','sent','failed'),
  attempts, last_error, sent_at
)
UNIQUE(care_event_id, scheduled_at, channel)   -- защита от дублей при повторном проходе планировщика

password_reset_tokens (
  id, user_id FK, token_hash UNIQUE, expires_at, used_at, created_at
)

api_tokens (
  id, user_id FK, name, token_hash UNIQUE, created_at, last_used_at, expires_at NULL, revoked_at NULL
)
```

Осознанно НЕ делаем отдельную таблицу `care_event_occurrences` поверх `notification_jobs` — для MVP одной таблицы-outbox достаточно и как очереди, и как истории отправок. Если понадобится лог «выполнено/не выполнено» по событию руками пользователем — это отдельная кнопка «отметить выполненным», которая просто пересчитывает `next_due_at` (см. раздел 5), без отдельной сущности.

## 5. Recurrence: решение по нюансу из раздела 3 анализа

Часть событий (полив, подкормка) имеет обычную календарную периодичность — для них `recurrence_kind='rrule'`, `recurrence_rule` в формате RFC 5545, и `rrule-go` сам считает следующий `next_due_at` после срабатывания.

Часть событий (обработка «до распускания почек», «на розовый бутон» и т.п.) привязана к фенофазе, а не к дате — календарное правило тут физически не может быть точным (см. раздел 11 анализа). Для них `recurrence_kind='manual'`: `recurrence_rule` пустой, `recurrence_note` — свободный текст (как сейчас в прототипе), а `next_due_at` после срабатывания **не пересчитывается автоматически** — пользователь сам отодвигает дату на следующий год через кнопку «Изменить» (уже есть в прототипе). Это самое простое решение, не требующее парсинга фенологии погоды/региона.

## 6. Домен Sender — подробно

```go
package sender

type Channel string
const (
    ChannelMAX      Channel = "max"
    ChannelVK       Channel = "vk"
    ChannelTelegram Channel = "telegram"
)

type Message struct {
    Title string
    Body  string
}

type Sender interface {
    Send(ctx context.Context, externalID string, msg Message) error
}

type Dispatcher struct {
    senders map[Channel]Sender
}

func (d *Dispatcher) Send(ctx context.Context, ch Channel, externalID string, msg Message) error {
    s, ok := d.senders[ch]
    if !ok { return ErrChannelNotConfigured }
    return s.Send(ctx, externalID, msg)
}
```

- `sender/max`, `sender/vk`, `sender/telegram` — три независимых пакета, каждый реализует `Sender`, инкапсулируя конкретную библиотеку (`max-bot-api-client-go`, `SevereCloud/vksdk`, `go-telegram/bot`). Токены ботов — только через переменные окружения/секрет-менеджер, в коде и в репозитории их не быть не должно.
- `outbox_worker.go`: горутина раз в N секунд выбирает `notification_jobs WHERE status='pending' AND scheduled_at<=now()` через `SELECT ... FOR UPDATE SKIP LOCKED` (это даёт идемпотентность и защиту от двойной отправки при нескольких инстансах — без внешнего лока), зовёт `Dispatcher.Send`, проставляет `sent`/`failed` + `attempts`/`last_error`. При `failed` — retry с backoff, максимум 3-5 попыток.
- Планировщик (`/internal/scheduler`) только читает `care_events`, создаёт строки в `notification_jobs` для **каждого канала, выбранного в событии** (без фолбеков и приоритетов) и продвигает `next_due_at` (если `recurrence_kind='rrule'`). Он никогда не вызывает `sender` напрямую — только пишет в очередь.

**Правила времени (решено):**

- Уведомления планируются на **утро** по местному времени пользователя: `scheduled_at` = `NOTIFY_HOUR` (константа/конфиг, по умолчанию 09:00) в часовом поясе `users.city_id → cities.timezone` в дату `next_due_at`, переведённое в UTC.
- Планировщик тикает часто (например, раз в 15–60 минут), а не раз в сутки, потому что у пользователей разные пояса. Условие выбора события: `active AND next_due_at <= (сегодняшняя дата в поясе пользователя)` и `last_notified_for IS DISTINCT FROM next_due_at`. Если утреннее время уже прошло (событие создано/перенесено на сегодня днём) — `scheduled_at = now()`, т.е. отправка при ближайшем проходе воркера.
- Воркер отправки сравнивает `scheduled_at <= time.Now()` (в UTC) — никакой логики часовых поясов внутри `sender`.
- Ежедневное событие (`rrule` с `FREQ=DAILY`): после создания job `next_due_at` сдвигается на завтра, следующий job создастся завтра утром — в тот же день дубля нет.
- Ручное событие (`manual`): job создаётся один раз, `last_notified_for := next_due_at`; повторно планировщик его не поднимет, пока пользователь не изменит дату («Изменить») или не нажмёт «выполнено».
- Если канал события не подключён (`user_channels.status != 'connected'`) — job сразу `failed` с понятным `last_error`, переотправки в другой канал нет.

## 7. Подключение каналов (экран «Каналы уведомлений»)

Общий паттерн для всех трёх платформ: **бот не может написать пользователю первым** (подтверждено исследованием — см. чат, Telegram через `/start`, VK — через явное разрешение сообщений от сообщества, MAX — аналогично требует первого действия от пользователя). Поэтому подключение — это всегда поток «инициирует пользователь»:

1. Пользователь на странице «Каналы» жмёт «Подключить» у нужного канала.
2. Бэкенд генерирует одноразовый `link_code` (короткий, с TTL ~15 минут), сохраняет в `user_channels` со статусом `pending`.
3. Фронтенд показывает инструкцию:
   - **Telegram** — тут проще всего: диплинк `https://t.me/<bot_username>?start=<link_code>` одной кнопкой открывает чат и сразу отправляет `/start <link_code>` — пользователю ничего печатать не надо.
   - **VK** — показать ссылку на сообщество + инструкцию «напишите любое сообщение, бот пришлёт код для подтверждения» (прямой диплинк с пэйлоадом для VK нужно проверить на этапе реализации — поведение `vk.me/<community>?ref=...` стоит протестировать вживую, это не гарантированно так же удобно, как у Telegram).
   - **MAX** — аналогично: ссылка на бота, пользователь пишет `/start <link_code>` сам (диплинк-параметры уточнить по актуальной документации MAX на момент реализации).
4. Вебхук-эндпоинт канала (`POST /webhooks/telegram`, `/webhooks/vk`, `/webhooks/max`) получает входящее сообщение, вытаскивает код, находит `user_channels` по коду, сохраняет `external_id` (chat_id/user_id платформы), меняет статус на `connected`.
5. Фронтенд поллингом (раз в 2-3 сек, максимум 2 минуты) проверяет статус — как только `connected`, показывает галочку и останавливает поллинг.
6. Кнопка «Отключить» — просто сбрасывает `external_id` и статус в `disconnected`.

**Важная оговорка, которую нужно проверить перед продакшеном (а не на этапе прототипирования):** по информации из не до конца проверенного источника, у MAX действуют ограничения на массовые/маркетинговые рассылки без отдельного договора с платформой, причём формулировки задевают и часть сервисных уведомлений. Это нужно явно сверить с официальным ToS/документацией MAX для ботов (`dev.max.ru`) до того, как закладывать MAX как единственный приоритетный канал в продакшене — если ограничение подтвердится, возможно, придётся трактовать канал иначе (например, только с явным договором) или понизить его приоритет относительно VK/Telegram.

**Сброс пароля по email (решено):** `password-reset/request` принимает email и отправляет на адрес, указанный при регистрации, письмо со ссылкой на `/reset-password?token=...`. Ответ всегда одинаковый (200), независимо от того, есть ли такой аккаунт. `password-reset/confirm` принимает токен и новый пароль, меняет пароль и отзывает все сессии и API-токены пользователя. Токен — случайный ≥256 бит, в БД хранится только его хэш, TTL 1 час, одноразовый. Rate-limit на `request` (по IP и по email).

Отправка писем — отдельный маленький пакет `/internal/mailer` (интерфейс `Mailer` + SMTP-реализация, параметры SMTP — только через env). Это **не** часть домена `sender` и не канал напоминаний. SMTP-провайдер — российский или собственный сервер (152-ФЗ), выбрать на этапе реализации; на локальной разработке — MailHog/Mailpit в docker-compose.

**Авторизация (решено): два способа, оба действуют на все ручки `/api/*` кроме `auth/*`:**

1. Сессионная cookie (httpOnly, Secure, SameSite=Lax) — для веб-интерфейса.
2. **Персональный API-токен** в заголовке `Authorization: Bearer <token>` — для скриптов и внешних клиентов. Токен создаётся пользователем в `/account`, показывается в открытом виде **один раз**, в БД хранится только хэш. У токена есть имя, `created_at`, `last_used_at`, опциональный `expires_at`; отзывается в любой момент.

Для запросов с Bearer CSRF-защита не нужна; для cookie-запросов с изменением данных — проверка заголовка `Origin`/`Sec-Fetch-Site`. Общий middleware определяет пользователя одним из двух способов; дальше хендлеры работают с `user_id`, не зная, как он получен.

Всё под этой авторизацией, кроме `/webhooks/*` (эти проверяются подписью/секретом платформы, не пользовательской сессией), `auth/*` и `/api/docs`, `/api/openapi.yaml` (открыты).

### 8.1. API-паритет и документация (обязательное правило)

**Принцип: API-first.** Любое действие, которое пользователь может сделать в системе, должно быть доступно через HTTP API и описано в документации. Фронтенд — просто один из клиентов этого API; «приватных» ручек, существующих только для React, быть не должно. Если появилось новое действие (создать/изменить/удалить/отметить/подключить и т.п.) — вместе с ним в том же PR появляется ручка в API и её описание в спеке.

**Документация:**

- Источник правды — `api/openapi.yaml` (OpenAPI 3.1), пишется вместе с ручкой, а не «потом». Встраивается в бинарник (`go:embed`).
- Раздаётся самим приложением: `GET /api/openapi.yaml` (сырая спека) и `GET /api/docs` (Swagger UI, статика встроена в бинарник, без внешних CDN).
- Для каждой операции в спеке обязательны: `summary` и описание на русском, схемы запроса/ответа, примеры, все возможные коды ответов (в т.ч. 400/401/403/404/422/429), требования к авторизации (`security`), единая схема ошибки.
- Webhooks (`/webhooks/*`) тоже описываются в спеке, но с тегом `internal` (вызываются платформами, не пользователями) — они исключение из правила паритета, перечисляются явно в allowlist теста.
- `/api/docs` и `/api/openapi.yaml` **открыты без авторизации**, в том числе на проде (решение владельца). В спеке описаны обе схемы авторизации (`securitySchemes`: cookie-сессия и `bearerAuth`), в Swagger UI работает кнопка «Authorize» для вставки Bearer-токена.
- Спека проходит валидацию (`kin-openapi`) в CI; невалидная спека = упавший тест.

**Реестр действий.** Каждая публичная операция доменного слоя (экспортируемый метод сервисов `auth`, `plants`, каналов и т.д.) регистрируется в `/internal/api/registry.go`:

```go
var Registry = map[string]Route{
    "plants.Create": {Method: "POST", Path: "/api/plants"},
    "plants.Update": {Method: "PATCH", Path: "/api/plants/{id}"},
    // ...
}
// Явные исключения — только с причиной, ревьюится отдельно:
var InternalOnly = map[string]string{
    "scheduler.Tick":     "фоновая задача, не действие пользователя",
    "sender.Dispatch":    "внутренний домен отправки",
}
```

**Тест паритета (`/internal/api/parity_test.go`) — обязан падать, если:**

1. В сервисе домена есть экспортируемый метод (находится через `reflect`), которого нет ни в `Registry`, ни в `InternalOnly` → «создано действие, но не создана ручка в API».
2. Действие есть в `Registry`, но соответствующего маршрута нет в реальном роутере (обход через `chi.Walk` по тому же роутеру, который собирает `cmd/server`).
3. Маршрут есть в роутере (кроме `InternalOnly`/служебных `/api/docs`, `/api/openapi.yaml`), но его нет в `openapi.yaml`.
4. Операция есть в `openapi.yaml`, но маршрута в роутере нет (протухшая документация).
5. У операции в спеке нет `summary`, схемы ответа или `security` (кроме явно публичных `auth/*`).

Тест запускается в CI на каждый PR и блокирует мерж. Он создаётся на шаге 1 чеклиста (с пустым реестром) и дальше только растёт — «зелёный» тест на любом шаге является частью Definition of Done.

**Фронтенд обязан ходить в API только через клиент, сгенерированный из `openapi.yaml`** (например, `openapi-typescript` + `openapi-fetch`) — это второй рубеж защиты: вызвать несуществующую ручку из React не получится на этапе компиляции.

## 9. UI-страницы фронтенда

Сверять по прототипу (https://claude.ai/artifact/Y4Rc3nSGwTTmzsSfdo6TkZ), один в один по полям/формулировкам/категориям:

1. **/login, /register, /forgot-password, /reset-password** — простые формы (регистрация: email + пароль + город).
2. **/ (дашборд)** — список растений + верхняя лента ближайших дел по всем растениям (как в прототипе).
3. **/plants/:id** — карточка растения: краткая сводка (годовая шкала по месяцам + «N событий в году, ближайшее — …») + кнопка «Показать все события» → разворачивает вкладки категорий и список событий с кнопкой «Изменить». Для пустого (только что созданного) растения — кнопка «подтянуть уход из внешнего источника» (см. раздел 10).
4. **/channels** — три карточки (MAX/VK/Telegram) со статусом и кнопкой подключения/отключения — логика из раздела 7.
5. **/account** — смена пароля, смена города, управление API-токенами (создать/отозвать), удаление аккаунта (важно для 152-ФЗ — право на удаление своих данных).

## 10. Автоподтягивание ухода из внешнего источника (уже есть в прототипе как мок)

В прототипе для нового пустого растения есть кнопка «Подтянуть базовый уход из внешнего источника» с атрибуцией на **Perenual (Plant Care API)** — в прототипе это заглушка без реального запроса. В MVP это можно оставить как есть (просто подставлять дефолтный набор событий) либо, если останется время, реально сходить в Perenual API по названию растения (бесплатный тариф — 100 запросов/день, см. раздел 8 анализа). Это **не блокер MVP** — помечено как опциональное улучшение, не обязательная часть выпуска.

## 11. Безопасность (минимально достаточный набор, не избыточный)

- Пароли — только `argon2id` (никогда не plain/MD5/SHA без соли).
- API-токены и токены сброса пароля — случайные ≥256 бит, в БД только хэш, значение показывается один раз; сброс пароля отзывает все сессии и API-токены.
- Сессии — случайный токен ≥256 бит, httpOnly + Secure + SameSite=Lax cookie, хранение сессий в БД с `expires_at`, возможность отозвать (logout = удалить строку).
- Токены ботов (MAX/VK/Telegram) — только в переменных окружения на сервере, не в репозитории, не в БД в открытом виде если это вообще не нужно (это секреты сервиса, не пользователя — для них env достаточно).
- `external_id` пользователя на сторонних платформах — обычные данные, шифрование at-rest не обязательно для MVP (не платёжные данные), но таблица `user_channels` должна быть доступна только через авторизованные ручки конкретного пользователя (проверка `user_id` на каждом запросе).
- HTTPS везде (Caddy с авто-TLS), HTTP редиректится на HTTPS.
- Rate-limit на `/api/auth/login` и `/api/auth/register` (простейший — in-memory token bucket по IP, без Redis).
- Валидация входных данных на бэкенде (не полагаться только на фронтенд-валидацию форм).
- Вебхуки платформ — проверка подписи/секрета (Telegram — секретный токен в заголовке, VK — `confirmation`/`secret` из Callback API, MAX — проверить актуальный механизм в документации на момент реализации).
- 152-ФЗ: хостинг в РФ-регионе (раздел 9 анализа), хранить минимум персональных данных (email, пароль-хэш, внешние ID мессенджеров — и всё), дать пользователю возможность удалить аккаунт и данные.

## 12. Порядок разработки (чеклист для агента)

1. Каркас проекта: Go-модуль, структура папок (раздел 3), `docker-compose.yml` (app + postgres + caddy), миграции базовых таблиц. **Каркас API-документации:** пустой `openapi.yaml`, раздача `/api/docs` и `/api/openapi.yaml`, реестр действий и **тест паритета (раздел 8.1)** — подключён в CI с первого дня.
2. Auth: регистрация (email + пароль + **выбор города из справочника `cities`**, сид справочника — в миграциях)/вход/логаут/сессии + сброс пароля по email (`/internal/mailer`, Mailpit локально) + API-токены (Bearer) + общий auth-middleware (cookie или Bearer). Простейший UI (формы входа/регистрации/сброса). Ручки описаны в спеке, действия внесены в реестр, тест паритета зелёный.
3. CRUD растений и событий (бэкенд + React UI по прототипу) — без каналов и планировщика, просто управление данными. Каждая ручка — сразу в `openapi.yaml`; фронтенд использует клиент, сгенерированный из спеки.
4. Планировщик: тикер, поиск `next_due_at<=now()`, запись в `notification_jobs` (без реальной отправки — для начала можно просто логировать в консоль).
5. Домен `sender`: интерфейс + outbox worker + **один** канал для сквозной проверки — Telegram (проще всего технически: один токен, без модерации). Довести цепочку «событие созрело → job → отправлено в Telegram» до конца.
6. Экран подключения каналов (раздел 7) для Telegram — диплинк + вебхук + поллинг статуса.
7. Добавить VK тем же паттерном.
8. Добавить MAX — после того, как прояснён вопрос из раздела 7 про ограничения на рассылки.
9. Финальная проверка документации: пройтись по `/api/docs` и вручную выполнить каждую операцию через «Try it out»; убедиться, что примеры и коды ошибок актуальны, `/account`, «отметить выполненным», дашборд-лента и импорт ухода покрыты ручками.
10. Задеплоить на VPS (Timeweb/Beget), проверить end-to-end на реальном аккаунте. `/api/docs` на проде — закрыть или оставить по решению владельца (см. открытые вопросы).
11. (Опционально, если останется время) — реальная интеграция с Perenual вместо мок-кнопки.

**Definition of Done для любого шага, добавляющего действие:** ручка в API + описание в `openapi.yaml` + запись в реестре + зелёный тест паритета. Без этого шаг не считается завершённым.

## 13. Что сознательно НЕ делаем в MVP (non-goals)

- Email как канал напоминаний и push-уведомления (ntfy/FCM/APNs) — не нужны, пока есть MAX/VK/Telegram. Email остаётся только для служебных писем (сброс пароля).
- WhatsApp — официально дорого (Business API), неофициально рискованно (бан номера) — не берём вообще на этом этапе.
- Нативное мобильное приложение — не нужно, веб-фронтенд достаточен.
- Многопользовательские роли/команды/шеринг растений между аккаунтами.
- ИИ-распознавание растений по фото, диагностика болезней — это ниша конкурентов (Planta/PlantIn), сознательно не копируем (см. раздел 1 анализа).
- Полноценная история/журнал выполненных событий — достаточно `notification_jobs` как лога отправок.
- Биллинг/подписки.
- Admin-панель — если нужно что-то поправить в проде на старте, это делается напрямую в БД.

- **БД-слой:** `database/sql` + драйвер `pgx/stdlib`, ручные запросы (sqlc не подключали), миграции `goose` (встроены в бинарник).
- **Справочник городов:** 1114 городов РФ (GeoNames, плюс Крым и Севастополь с поясом Europe/Moscow — вручную в gen_cities.py, CC BY 4.0) с IANA-поясами и регионом на русском; `scripts/gen_cities.py` пересобирает CSV, сид идёт при первом старте.
- **Каналы:** Telegram — `go-telegram/bot`, VK — `vksdk`, MAX — прямой HTTP к `platform-api.max.ru` (формат апдейтов и диплинка MAX **сверить с dev.max.ru** до продакшена, как и ограничения на рассылки из раздела 7).
- **Dev-режим:** при пустых токенах и `DEV_FAKE_SENDERS=true` отправщик-заглушка пишет сообщения в лог и таблицу `dev_outbox`; в `APP_ENV=prod` заглушки отключены.
- **Время:** планировщик тикает раз в `SCHEDULER_INTERVAL` (1 мин), уведомление планируется на `NOTIFY_HOUR` (9:00) местного времени города пользователя; если утро уже прошло — «на сейчас».
- **Тесты:** `make test` — парити-тест 8.1 + интеграционные (планировщик по поясам, daily/manual, без фолбеков, outbox с ретраями, auth/сброс пароля/токены, изоляция пользователей).
- **Не сделано:** реальная интеграция с Perenual (кнопка подставляет базовый набор), rate-limit по email для `/auth/login` (есть по IP), деплой.

### Справочник Perenual (уточнение, 23.11.2026)

- **Дефолтных событий нет.** События предлагаются только из данных справочника (полив, обрезка); если данных нет — событий нет, а интерфейс и API (`coverage`, `notice`) явно говорят, что именно не подтянулось.
- **Поиск вариантов:** `GET /api/plant-reference/search?q=` показывает, какие виды и сорта есть в справочнике (с пометкой, доступны ли по ним данные ухода на текущем тарифе). Выбранный вид берётся через `GET /api/plants/{id}/care-suggestions?species_id=`.
- **Точность совпадения:** `match.quality` = `exact` | `approximate` | `chosen` с пояснением (например, «слива бербанк» → ищется «plum», сорт справочником не различается).
- **Сохранение:** `POST /api/plants/{id}/events/import` принимает только явный непустой список событий.
